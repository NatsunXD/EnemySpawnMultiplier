Enemy Spawn Multiplier - v16 and v16.12 preview packages

Close the game before upgrading. Remove previous Enemy Spawn Multiplier entries
and install exactly one package:

- Enemy-Spawn-Multiplier-6x-Native-Composition-v16.zip
- Enemy-Spawn-Multiplier-6x-Light-Medium-Bias-v16.zip
- Enemy-Spawn-Multiplier-Preview-Low-Budget-Fast-Cadence-v16.12-preview.zip

Install and enable the official Bingus Shared Loader v15 or newer, deploy with
HDArsenal or HD2MM, and restart the game. All packages use the same resource ID
and cannot be combined.

What v16.12 changes
-------------------

Three settings moved at once:

1. Reinforcement budget 0.1x -> 0.2x. The effective cfg+0x78 override is still
   forced to the already-scaled director base, so a positive native override
   cannot bypass the reduction.

2. Patrol squad size 3x -> 10x via cfg+0x3F8
   travelers_max_unit_count_multiplier. game.dll+0x943E40 computes a patrol
   wave as round(base_units * that curve), so this is the lever that changes how
   many units appear per patrol.

3. Encounter templates now favour heavier squads. Candidates are ranked by cost
   per planned unit; the cheapest half is suppressed to 0.25x weight, the middle
   30% is left at 1.0x, and the costliest 20% is boosted to 4.0x. Cost per
   planned unit is the closest available proxy for armour class, so the expensive
   end is where the heavy units live.

Unchanged: reinforcement cooldown clamp at 2 s, patrol spawn cooldown 3x, patrol
count 3x, timed Patrol/Straggler intervals pinned at 0.0-0.1 s, nonzero per-type
caps and group clamp at 10x, GuardForce/static defenders fully native, no
executable-code changes.

Interactions worth knowing
--------------------------

Budget and squad size pull in opposite directions. The 0.2x budget buys fewer
composition points per wave, so each wave spends its points on fewer template
entries - but each entry is now up to 10x larger and biased toward expensive
templates. The net visible count is not simply 0.2x times 10x; observe it rather
than predict it.

A 10x patrol wave can also reach the shared native population gate sooner.
Position queries, the 96-slot queue, the effective-70 term and the 448 component
cap all still apply. If reinforcement waves start getting rejected once many
patrols are alive, that gate is the reason, not the curve writes.

Reversal is cheap: set modifier_travelers_max_unit back to 3.0 or 1.0, or disable
modifier_scale_enabled, and rebuild.

Reading the log
---------------

- p=   Encounter budget current/original. With a native 600 this now reads
       120.0/600.0.
- o=   effective cfg+0x78 override. Expect 120.00.
- ms=  applied curve scales, expected 3.0/3.0/3.0/10.0.
- mv=  live head float of each scaled curve. With a baseline of 1.0 this reads
       3.00/3.00/3.00/10.00.
- w=   biased/available candidates. With heavy bias enabled the first number is
       the candidate count that was reweighted.
- e=, a=, b=, d=, fl=  reinforcement deadline and timed-scheduler gate inputs.

To uninstall, close the game, disable this mod, purge deployment, and redeploy
the remaining mods.
